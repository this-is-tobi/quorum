# Threat model

What an attacker can do to a review, what quorum protects, which controls stand in the way today, and what remains. Read it before you run quorum on changes you did not write: none of it is a setting to turn on, it is how quorum works.

## The attacker

Quorum feeds text an attacker controls to language models and reports what they answer. The attacker is anyone who can open a pull request, from a fork included, and they control the whole diff: its code, comments, strings and file names, and the commit messages a `git format-patch` series carries. They control every file of the pull request's branch too, so guidelines a caller loads from that branch's checkout are theirs as well, and so are a config file and the prompt files it names.

What quorum answers goes to the report on stdout, the JSON result on a pipe or a file, and the lines on stderr, and from there to CI logs, terminals and whatever renders the result. `quorum bench` prints its Markdown report on stdout instead of the result, and writes its run directory, where `results.jsonl` holds each review's full result. It usually runs in CI, with a model API key in its environment.

## Assets

| Asset | The attacker wants to | What stands in the way |
| --- | --- | --- |
| Verdict integrity | Suppress a real finding, sway a verdict, or forge a finding | Code-derived evidence, strict parsing, blind votes and arithmetic confidence, within the limits of the [residual risk](#residual-risk) |
| Secrets: the model key, a CI token, repository credentials, and a change's own secrets | Have a model read or leak them, or have the change's own secret reach a hosted model | A model path with no tool and no secret, a key sent only to its own endpoint, and a binary that reads nothing from the working directory, a config file included unless it is named; and a change's own secrets, a file named as one or holding a credential, held back from every request: [Secrets held back](#secrets-held-back) |
| Output channels: CI logs, terminals, what renders the result | Turn model text into markup, a link, a workflow command or an escape sequence | The CLI makes the text it writes inert for a terminal and a GitHub Actions log; anything else that renders the result, or reads a bench's `results.jsonl`, must treat its text as untrusted: [Output handling](./30-output-handling.md) |
| Availability and spend | Multiply the calls and their cost with a huge or finding-flooding pull request | `maxFindings`, the concurrency limit, each call's deadline and its bounded retries, the reply's limit, the token cap and the review's deadline, which bound a large change's parts as they bound every call, and, for a path review, whose size is the tree's, the large gate: it prints the estimate and refuses before any call a review whose research may pass the cap, unless `--large` is given ([What a path review costs](../20-using/15-sources.md#what-a-path-review-costs)) |
| Coverage | Have the run review less than the whole change, silently | [Research in parts](#research-in-parts), which reads a large change whole within each model's window and never clips a hunk; the size guard, which refuses a request that may not fit; each profile's coverage, which lists every file and the lines left unreviewed; and unreviewed findings and incomplete reviews, exit `4`, for the gaps the harness detects, a file whose change the diff does not carry, a file held back as a secret and a hunk too large for any window among them; what the guard cannot know is not one of them: [What the harness cannot detect](#what-the-harness-cannot-detect) |
| The machine that runs quorum | Run a program through a repository's config, attributes, hooks or a revision | Quorum's own git: [Git, run by quorum](#git-run-by-quorum) |

## Residual risk

A determined adaptive attacker may suppress or sway findings. In published studies no prompt-level defense held under adaptive attack, and a panel of blind voters filters false positives but cannot restore a finding the finder never proposed. Quorum keeps the model path harmless, raises the cost of an attack, and shows a human where to look: each verdict's vote split, its `quoteMatched` flag (whether the code the finder quoted appears in the evidence), the `invalidFindings` count of findings that cited code outside the diff, the unreviewed findings, the advisory flags of `meta.flags`, and the entries of `meta.incomplete`. It assists a reviewer; it does not replace human review of untrusted changes. How far planted text sways each class of model is measured by the bench's injection corpus: [Measurement](./40-measurement.md).

With no tool and no secret in the model path, the incident classes of 2025 and 2026, token theft and code execution through an AI agent in CI, do not apply. What remains is verdict manipulation, the places where model text is rendered, cost, and files that look trusted, such as guidelines or a config read from the pull request's checkout.

## Controls in place

### A model path with no tool and no secret

A provider receives text and returns text. Quorum offers no tool, function, file or network capability to a model, and the request type has no field for one. Each shipped adapter refuses, in a program's `extraBody`, the body fields of its protocol that would offer one, such as `tools`, OpenRouter's `plugins`, Anthropic's `mcp_servers` or Gemini's `cachedContent`, in any letter case and with or without underscores: [The tool fields](../20-using/30-providers.md#the-tool-fields). A model id can bring tools of its own, which no body check sees, so a provider built from a preset, or pointed at a preset's origin, refuses the ids its vendor documents as running tools by themselves: OpenAI's search models, which search the web before every answer, OpenRouter's `:online` models, which add a web search, and Groq's gpt-oss, which searches the web by itself, among others: [The model ids a preset refuses](../20-using/30-providers.md#the-model-ids-a-preset-refuses). `fromConfig` builds each provider a config defines from its preset or its protocol, through these refusals, and the CLI builds its providers through `fromConfig`: [`loadConfig` and `fromConfig`](../95-reference/30-library-api.md#loadconfig-and-fromconfig). A program that passes a preset's values to an adapter itself gets only the adapter's checks. The refusals of the body fields apply to every adapter today, and the reply check of `openaiCompatible` is the one that covers a tool a model id brings: a reply that shows a tool the server ran, Groq's `executed_tools` or a `url_citation` annotation, fails the call. That check runs after the server ran the tool. It keeps a review from being built on the tool's output, but what the tool sent has already left, and a search query can quote the diff. Groq reports `executed_tools` whatever the model does, while a `url_citation` appears only when the reply cites a source, so a search model that cites nothing can pass: choose a model that runs no tool. A finder that fails is a `research-failed` gap of its profile, and a voter's failure is recorded as a failed vote: [Failed votes](../20-using/50-lenses-and-policy.md#failed-votes). Two gaps remain. A model id no preset knows, or one reached through a gateway or a proxy at another origin, can still bring tools, and only a reply that reports them to `openaiCompatible` is caught: the `anthropic`, `gemini` and `ollama` readers do no such check. And `headers` are sent as given. A program that sets either breaks this control. On the `claude-code` protocol the one tool a model has is the schema tool, which only captures the reply, and the key of `api-key` mode goes in the child's environment alone: [Claude Code, isolated](#claude-code-isolated). No environment value, key, token or credential appears in any request: keys live in the adapters, and the core never reads the environment. The suite checks with fake providers that no environment value reaches a request, the CLI's key variables included.

### A key sent only to its own endpoint

Each shipped adapter sends its `apiKey` only in the header its `auth` names, `Authorization` by default and `x-goog-api-key` for `gemini`, and never in a URL, a body or another header. Three further rules keep the key from leaking:

- **A base URL may not carry credentials.** A user name or a password is a configuration error, and the key goes in `apiKey`.
- **No redirect is followed.** A redirect is an error, so the key header never reaches another endpoint.
- **Server text is redacted.** The key, the base URL's path and the values of the `headers` option, as written and trimmed, are replaced with `[redacted]` in any server text an error quotes. The `query` option is not redacted, so never put a key there: a `query` value equal to the key is refused.

The CLI reads its providers through the config layer of `loadConfig` and `fromConfig`, which keeps the same rule and starts from a named config being trusted: it chooses where each key goes, and a TS or JS config runs code, so in CI it must come from the base branch or from outside the pull request's checkout, its prompt files with it, never from the pull request under review: [Trust](../20-using/20-configuration.md#trust). Under that, a panel that the `QUORUM_VOTER_*` variables derive onto another origin than the finder's keeps no key, header, query parameter, body field or model of the finder's provider, so no fallback carries a key to another endpoint, or from `https` to `http`: [The voter's fallback](../20-using/20-configuration.md#the-voters-fallback). A preset's own key variable is read only at the preset's origin, which for `azure-openai`, whose preset has no base URL, is any `https` host ending in `.openai.azure.com`. An explicit `apiKeyEnv` or a literal `apiKey` follows a `QUORUM_<ROLE>_BASE_URL` override of its own provider, since that override changes the provider and is no fallback. [The keys](../95-reference/30-library-api.md#keys) has the order and the rest.

### Nothing read from the working directory

In CI, quorum runs inside the checkout of the pull request it reviews, a directory the attacker writes. Quorum looks for no config file there: it reads one only when `--config` or `QUORUM_CONFIG` names it, and never a `quorum.config.yaml`, a `quorum.yaml` or a `quorum.config.mts` it finds, since a file found in the checkout would be the attacker's. A YAML or JSON one could point a provider's `baseUrl` at the attacker's server while its `apiKeyEnv` names the job's real key, and a TS or JS one would run in the job. A Bun-compiled binary loads a `.env` and a `bunfig.toml` from its working directory by default: a `bunfig.toml` can `preload` code, which then runs with the job's secrets, and a `.env` can set any variable the environment leaves unset, such as the one that chooses the finder's endpoint, which would then receive its key. `bun run compile` turns both off, and a test holds the script to it. Bun itself, as `bun run start` or `bun ./src/cli/bin.ts`, reads both from the directory it runs in, before any of quorum's code runs. A planted `.env` can then set `QUORUM_CONFIG`, and so name a config of the pull request's. The binary reads no `.env`, nor does Node, which runs the npm package's `quorum`. So run the binary, or the `quorum` that `npm install -g` puts on your `PATH`, in a checkout you do not control, never Bun, and never run the package through `npx`, `npm exec` or `pnpm dlx` there: they read the checkout's `.npmrc`, which can name another registry for the package to come from, where `npm install -g` does not read the project's `.npmrc`.

### Claude Code, isolated

A `claude-code` provider starts a process inside the job, which is more than text in and text out, so it is held to the same rule: no tool but the schema tool, no key that quorum picks, holds or sets in the default modes, nothing read from the working directory. `claude` runs in an empty directory made for the request, with `--tools ''`, `--setting-sources ''`, `--strict-mcp-config`, `--no-session-persistence` and `--disable-slash-commands`, the system text in a file and the message on stdin, so no key or prompt is on a command line that `ps` shows. A message that starts with `/` is refused, since `-p` would run it as a command. **File mentions are closed.** Without the attachment and mention variables, a line in the diff such as `@/home/runner/.config/gh/hosts.yml` makes Claude Code attach that file for the model to read, with every tool off: the content then goes to the model, and an injected request can ask for it in a finding's `summary`, which the CLI prints. That was observed live with 2.1.311, with a canary file, and with the variables set the model saw none. The live check repeats it with a fresh token. Its environment loses the parent session's variables and the ones that load plugins, skills, tools, a process wrapper or extra request body, and turns off auto memory, compaction, the IDE connection, the claude.ai connectors, attachments, file mentions, `CLAUDE.md` files and the bundled and managed skills. Under `login` and `api-key` it also loses the credential, header and endpoint variables that the `login` row of [The auth modes](../20-using/30-providers.md#the-auth-modes) lists, and every `CLAUDE_CODE_USE_` variable, so a login or a key never reaches another host. Any other variable the job's environment holds passes through to `claude`, and keeping it clean is the operator's. Under `api-key`, `--bare` is documented to make Claude Code read no OAuth token, even if one is present (from Claude Code's documentation, not observed live). A text quoted from `claude` is redacted of the values of the credential variables that the redaction bullet of [The auth modes](../20-using/30-providers.md#the-auth-modes) lists, and of nothing else. The child leads a process group that an abort stops whole, and that quorum's own exit (`process.exit`, a second interrupt) kills too, and the request's directory, its working directory, its scratch files and the system text, is removed once it exits, or when quorum does. [The isolation](../20-using/30-providers.md#the-isolation) lists each measure and what it stops. The CLI's resolution, and `fromConfig`, never search the checkout for the executable: a data file cannot name it, a relative `QUORUM_CLAUDE_CODE_COMMAND` is refused, and the relative and empty entries of `PATH` are skipped. A program that calls `claudeCode` itself with a bare `command` gets `spawn`'s own `PATH` search.

What remains, stated plainly. A statement here that rests on Claude Code's documentation, and was not observed live, says so:

- **Managed policy may still load.** From Claude Code's documentation, and unverified live: an organization's managed settings, hooks and MCP servers are not skipped by `--setting-sources`. On a machine that has them, they may run in every review. The managed `CLAUDE.md` and managed skills, and the bundled skills, have variables that turn them off, which the child's environment sets (`CLAUDE_CODE_DISABLE_CLAUDE_MDS`, `CLAUDE_CODE_DISABLE_POLICY_SKILLS` and `CLAUDE_CODE_DISABLE_BUNDLED_SKILLS`): turned off by variables, unverified live on a managed machine.
- **Claude Code adds its own context to every request**: its environment details, the account's e-mail and the date, as a model's own account of its context shows. A prompt-injected diff can make a model echo the e-mail into a finding. `api-key` mode's `--bare` is documented to drop that context; that was not run live, and the other modes send it.
- **A run binds a cross-session inbox socket.** A `-p` run binds a socket and writes registry files under `~/.claude/sessions` while it lives, and Claude Code handles a message from a peer session by its default policy, a held one expiring after 5 minutes. With `CLAUDE_CODE_TMPDIR`, which quorum sets, the socket is created in the run's own directory (`tmp/cc-socks`, seen in the leftovers of real runs) and removed with it, so it never sits in `/tmp`. The registry files under `~/.claude/sessions` remain: they were gone after a normal exit, and a SIGKILL of quorum can leave one, and the run's directory with its socket, which was not checked. Having it refuse peer messages, `crossSessionInbound`, is for later.
- **Claude Code's own network calls follow the user's settings.** From Claude Code's documentation, not observed live: its update checks, telemetry and feature-flag fetches follow the user's own settings and variables, and quorum sets none of them: `DISABLE_AUTOUPDATER`, `DISABLE_TELEMETRY` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` turn them off, for the operator to set. An operator's own OpenTelemetry settings in the environment can make Claude Code export the prompt, the diff included, to the operator's collector; quorum leaves that to the operator.
- **Claude Code's home files are read, and may be written.** From Claude Code's documentation, not observed live: it always reads `~/.claude.json`, and may write there and under `~/.claude`, such as session files. What a run adds was not checked.
- **The schema tool is a tool.** `--json-schema` adds one, which only captures the reply as structured output, and `structuredOutput: 'prompt'` drops it, leaving the reply's shape to the prompt.
- **`inherit` skips the credentials a settings file configures.** From Claude Code's documentation, not observed live: no settings file is read, so an `apiKeyHelper`, or a cloud provider or base URL that an `env` block sets, does not apply: `inherit` is your own `claude -p` for the environment's variables only. It can fail to authenticate where your own shell would not.
- **The child holds the job's environment.** Every variable a mode does not remove reaches `claude`, the job's tokens included. Quorum sends them nowhere else, stores and logs none, and reads the credential variables it lists to redact their values from a quoted error, and under `api-key` to pass the key on to `claude`, and whether `ANTHROPIC_API_KEY` is set, for the billing warning. No tool of the model can read the environment, but a managed hook may. Run quorum with the variables it needs, and give a program that wants less an `env` of its own: [`loadConfig` and `fromConfig`](../95-reference/30-library-api.md#loadconfig-and-fromconfig).
- **The isolation depends on the Claude Code version, so quorum requires 2.1.311 or newer.** A Claude Code that lacks one of the flags fails the run, which is closed, but one that ignores an environment variable of the isolation runs with less of it, and for the attachment variables that is a file leak. So before its first request a provider runs `claude --version` and refuses a version below 2.1.311, or an output that names none, as a `process` failure: [Stopping, nesting and the version](../20-using/30-providers.md#stopping-nesting-and-the-version). The check trusts what `claude` prints, so it catches an old CLI, not a hostile one: the command must come from a trusted place.
- **A process outside the group, and a SIGKILL of quorum, are beyond the cleanup.** A helper that `claude` starts in a session of its own is out of reach of a signal sent to the group: when `claude` exits, quorum closes the pipes after 2 seconds so the call settles, and leaves the helper running. The exit handler kills each live group and removes each directory, but a SIGKILL of quorum, or a death by a default signal, runs no handler, and a runner that kills by process group does not reach a detached one. Those leave `claude` running until it ends, a cost and not a leak, and the directory holds no secret.
- **The command must come from a trusted place.** Quorum skips a relative or empty `PATH` entry and refuses a relative command, but an absolute `PATH` entry inside the checkout, such as a `node_modules/.bin` the pull request fills, is the operator's to avoid: quorum cannot tell it from any other. In CI, name the executable absolutely, `QUORUM_CLAUDE_CODE_COMMAND=/usr/local/bin/claude`, at a path the pull request cannot write.

### Strict single-object parsing

Every reply must hold exactly one JSON object, and quorum fails closed instead of guessing:

- A reply holding several different objects is refused: text echoed from the diff could pose as the answer. The same object twice, such as a fenced copy beside a prose copy, is accepted.
- A group that opens like a JSON object, `{` then `"` or the end of the reply, but never closes or does not parse, fails the reply: it is cut off or malformed, and an object quoted inside it or echoed beside it could be planted.
- An object that repeats a key is refused, since parsing keeps the last value and planted text that closes a string early could supply it.
- Text after the answer that reads like JSON syntax, a quote, a brace or a bracket, fails the reply: it is what the model's own continuation leaves when planted text closed a string and the object early. Plain prose after the answer, and code fence markers, are accepted.
- Closed reasoning blocks (`<think>`) are dropped in one linear pass, and an object that starts after a `<think>` that never closes is a draft, never read as the answer.
- A reply over 1,000,000 characters is refused before it is read, and one with more than 100 brace groups is refused as it is scanned, so a reply built to be expensive stays cheap.

The research reply must then be exactly `{ "findings": [...] }`: a missing array, or any other top-level key, is that part's `research-failed` gap, so a malformed reply never reads as "no findings" (exit `4` for a gating profile). A finding that does not match the schema, or holds an object or array under a key the schema does not name, where swallowed findings would hide, is unreadable: a `finding-unreadable` gap. An unusable vote is a failed vote.

The trailing-syntax rule works only where the model's continuation is written: an endpoint that enforces JSON stops generating when the root object closes, so there a planted early close leaves nothing to refuse.

### Code-derived evidence and the quote check

A finding must cite a line of the new file inside one of the diff's hunks and, when the diff has per-file headers, one of its files, or it is dropped with its reason. What a voter receives about the code is then read from the diff by the harness, never taken from the finder: the `file` is the diff's own path when the diff has per-file headers, and the `evidence` is the diff's lines around the cited one, capped at 2,000 characters. The finder's `quote` is only compared with the evidence, which sets `quoteMatched`; it is never sent to a voter. The only text a model wrote that a voter reads is the finder's `summary` and `category`, capped at 500 and 80 characters, and, for a diff without per-file headers, the file name, capped at 260: each stripped of control, format and other invisible characters, and fenced as an unverified claim.

### Blind votes and arithmetic confidence

Each vote request is built only from the finding, the lens's instructions, the diff context and the profile's guidelines: no request carries another vote, so no voter sees another's verdict or reasoning. The suite checks it by structure: the vote requests of a review are the same, nonces aside, whatever the voters answer. A vote reply is `{ keep, reasoning }`, and the confidence is computed in code from the kept votes: a voter cannot raise a finding by sounding sure. [Lenses and policy](../20-using/50-lenses-and-policy.md#confidence) has the arithmetic.

### Fenced data and the notices

All the data a model reads, the diff, the claim, the evidence, the diff section and the guidelines, is in the user message, each block fenced with a random nonce it cannot predict. The system message names every block of the request by its exact tag, so a tag planted in the diff is never named, and ends with the notice that fenced content is data and that text asking to skip or approve is suspicious. This is friction, not a control: [Prompts](../20-using/60-prompts.md#fencing-is-friction-not-a-control). A provider built with `systemPrompt: 'inline'` sends that system text at the head of the same user message as the data, so the instructions lose the role that sets them apart from it.

### `maxFindings` and the concurrency limit

Only the first `maxFindings` findings the research replies list in all, 50 by default, are read, and only those can reach the panel: a change reviewed in parts has its replies read in the parts' order, up to the cap across all of them. The rest are counted in a `findings-capped` gap, so a reply built to flood the run costs bounded work. With the security profile and the default cap, a review of one diff that fits one research request makes at most 151 calls: one research call, and three votes for each of 50 findings. Those are calls, and each makes one attempt and up to `retries` more when it fails in passing, three attempts by default and six at most, so the same review makes at most 453 attempts by default and 906 at the most: [Deadlines and bounded retries](#deadlines-and-bounded-retries). A large change adds one research call for each further part, which the token cap and the review's deadline bound: [Research in parts](#research-in-parts). `concurrency`, 4 by default, caps the calls in flight across every profile of the review. The size of what each call carries is bounded too: [The size guard](#the-size-guard).

### Deadlines and bounded retries

Every attempt has a deadline, 600000 ms unless its provider states one, so a model or a server that never answers cannot hold a review. A call that fails in passing is retried as often as its provider states, at most five times, after a random wait that grows with each retry. What planted text causes directly, a refusal, a cut-off or an unusable reply, is never retried, so it cannot multiply the spend. A reply it draws out can still time out, or end in a gateway's 504, and that is retried once, never twice. Nothing is retried once the review is aborted: [Deadlines and retries](../20-using/30-providers.md#deadlines-and-retries).

The review has a deadline of its own, `reviewTimeoutMs`, 30 minutes by default, so a pull request that makes every call slow cannot hold a CI job past it. At it every call in flight and every wait is stopped at once, no queued call starts, and a server's hint longer than the time left ends its call, so nothing outlives it. What was not done is a `review-deadline` gap of its profile, never a failed run, and no flag lifts a gating profile's gap: a pull request can cause it directly, with text that draws replies out. [The review's deadline](../20-using/20-configuration.md#the-reviews-deadline)

### The token cap

Denial of wallet is a named threat: OWASP lists unbounded consumption as LLM10:2025, and MITRE ATLAS names cost harvesting. A pull request drives it with decoy findings, which each cost a panel of votes, and with text that draws a reply out. `maxFindings`, the deadlines and the reply's limit bound each part, and none of them bounds the sum. A review spends at most `maxReviewTokens`, 2000000 by default, input and output, every attempt counted: [The token cap](../20-using/20-configuration.md#the-token-cap).

- **It reserves before it sends.** Each attempt reserves its worst case in the review's ledger before it is sent and settles when it ends, inside the call's slot, so calls in flight at once cannot overshoot the cap between them. A check after each call lets every slot pass it once, by what one call spends, and a diff of decoy findings makes that as many calls as the concurrency allows.
- **An attempt that does not fit is not sent.** It is a `token-cap` gap of its profile, never a failed run, and a gating profile's gap exits `4` whatever the flags: no flag lifts it, since a pull request causes it directly.
- **A failure that reports nothing counts the whole reservation**, and only a failure the server refused before any work counts nothing, so a request that fails cannot be made to look cheap.
- **The cap trusts the usage a reply reports**, so a server that reports less than it spent is counted at what it reports.
- **What is left.** A provider that spends more than it states is counted when it settles, so the calls in flight can pass the cap by that much. Claude Code continues a reply cut at its limit, up to three times a turn, and retries a failed call on its own: the reservation counts neither, and the usage it reports does. Gemini can report thought tokens past `maxOutputTokens`. The cap then refuses what no longer fits, so the overshoot is bounded by the calls in flight, and a new attempt never starts on top of it.

### The size guard

A model that reads less than the whole diff can miss what an attacker put in the part it did not read, and quorum cannot see what a model read. So it bounds what it sends, and refuses what may not fit:

- **The diff is read to 16 MiB and no further.** A larger one is refused before any request, with exit `2`.
- **Every request is bounded before it is sent**, the research request and each vote alike. One token per UTF-8 byte of its text, each code point at its longest form (as it is, decomposed, or compatibility-decomposed), plus 512 tokens for the chat template (4096 for `claude-code`, which adds its own context) and the request's reply budget (derived from the window, at most `maxTokens` when that is set, else 16000) must fit the `contextTokens` that the provider states for its model. Every provider defined as data, an HTTP one or a `claude-code` one, must state one, and a provider without one is a configuration error, exit `2`. What the bound costs, and how to raise it knowingly: [The context size](../20-using/20-configuration.md#the-context-size).
- **A request over the bound is a gap, and no flag lifts it for a gating profile.** Nothing over the bound is sent. A research request is split into parts first ([Research in parts](#research-in-parts)), so only a part its provider refused all the same, or a hunk too large for any part, is a gap there. A vote whose voter's window does not hold the cited file's section takes the section's header and the hunks nearest the cited line, and only a cited hunk that does not fit alone is still a `request-too-large` gap. The review records a `request-too-large` gap, or a `too-large` gap for a hunk no part holds, and keeps what it can still review, and the CLI exits `4` for a gating profile even with `--allow-incomplete`; a kept finding of a gating profile at or above its fail-on level, `high` by default, still exits `1`.

The flag stays out of reach because of the padding attack. A pull request that pads one hunk until no request of the window holds it needs no persuasion of any model, and a flag that waved the gap through would let the padding push a finding out of the reviewed text. `--allow-incomplete` lifts only a vote that failed in passing, never a gap a pull request can cause directly: decoy findings that push a real one past `maxFindings`, decoy findings and drawn-out replies that spend the review's token cap (a `token-cap` gap) or hold it until its deadline (a `review-deadline` gap), a binary or submodule file, a file held back as a secret, or text that makes a voter refuse, run on or answer unreadably. [Unreviewed and incomplete reviews](#unreviewed-and-incomplete-reviews) says which. This is also why no ratio of bytes to tokens is offered: encoded content takes 1 to 1.5 bytes per token, so any ratio above one lets the padding past.

### Research in parts

A change larger than one research request is reviewed in parts, each a research request of its own, and not refused: [Research in parts](../20-using/20-configuration.md#research-in-parts) says what a part holds. What that defends against, and what it leaves:

- **Parts against dilution.** In the one measurement of the same attack reviewed in one window and in parts, 16 to 22 percent of the attacks were caught when they sat beside benign changes in one window, against 50 to 60 percent when each change was reviewed on its own, and models read a long prompt worse well before their window is full. So `partTokens` sits at 32768, below most windows, and a change that fits its window but not `partTokens` is split too.
- **Never clipped.** A tool that cuts an oversized file's tail lets its author aim a payload there. Quorum splits a file only between its hunks, each piece with the file's header, and never inside a hunk. A hunk too large for the window, or a section with no hunk that is, is a `too-large` gap, listed in the profile's coverage ([Coverage](../95-reference/20-json-result.md#coverage)), and no flag lifts it for a gating profile, since a pull request causes it with one large hunk: exit `4`.
- **The files list is data.** Each part's request names the change's files, and the names are the author's. Each is shown with its hidden characters as `<U+XXXX>`, one per line, inside a fence, and the list is cut at 100 names and at a quarter of the lesser of the room a request leaves and `partTokens`, with `and N more` counting the rest, so a change of a hundred thousand files costs a bounded share of every part's request, whatever the window. When the list would leave a hunk out that a part holds without it, the names are dropped from every part and the block reads `and N more` alone.
- **A large change spends up to the cap.** Where 0.5.0 refused a diff over the window at once, a diff of several megabytes is now many parts, each one call. Each is reserved by the token cap and stopped by the review's deadline, and a profile's parts run at most `concurrency` at once, so the cap bounds what the change spends and what it stops is a `token-cap` or `review-deadline` gap that counts its parts. The parts after the first that a limit stopped are not sent.
- **A vote's partial context.** In 0.5.0, padding the cited file until its vote request did not fit gave a `request-too-large` gap, which no flag lifts. Now a voter whose window does not hold the cited file's section is shown the section's header and the hunks nearest the cited line, so the padding chooses what that voter does not see: an author can put benign hunks beside the cited line, and the code that shows reachability far from it. The security profile's voters keep a finding only when convinced (`Default keep=false unless genuinely convinced`), so a partial context leans toward a discard, and a flaw whose proof sits in a hunk the voter did not see can be discarded. Nothing in `meta` records that a verdict rests on part of a section, and a voter that states no room is sent the whole section as before.
- **What is left.** A part reads its own files and the list of the others, not their code, so a flaw that spans files in two parts can be missed, and the parts follow the diff's order, not their risk.

### Recovering a cut-off part

Reviewed content can force a reply to its limit: a hunk that makes the finder reason at length, or list a finding per line, or write a quote the size of the hunk. A research part whose reply is cut off, or lists as many findings as it was asked for at most, is recovered by splitting it in two, by code, and each half is asked as a part: [Recovering a cut-off part](../20-using/20-configuration.md#recovering-a-cut-off-part) says how. What that defends against, and what it leaves:

- **A bound, whatever the content.** An output-length attack can cut off every piece at every depth, so recovery stops at one hunk or at three splits deep, whichever comes first: a part makes at most 15 research calls (1, then 2, 4 and 8 pieces), and in tokens at most its own reservation plus `3d + 14h + 14 (r - d + e)` (`d` the part's diff tokens, `r` its reservation, `h` its largest file header and `e` the tokens a piece's request holds beyond its part's, its position line and, for a change in one request, the parts block), since each of the three depths holds the diff once with at most one repeated header per piece. Every piece is reserved by the token cap and stopped by the deadline, and a limit that stops one piece stops the part's later pieces and the profile's later parts, so the attack buys a constant multiple of the part and never more than the cap. The adaptations of a provider add, per setting, at most `concurrency` calls sent once more ([What quorum adapts by itself](#what-quorum-adapts-by-itself)).
- **No salvage.** The text of a cut reply is never read, its closed findings included, and no text of it reaches a piece or a voter: a piece's request is its part's with the piece's own text, and the cut reply's closed findings would be the model's, chosen by the content that forced the cut. The pieces' replies stand in its place.
- **What is still cut off is a gap no flag lifts.** A hunk whose piece is cut off even alone is `reply-cut-off`, with its lines in the profile's coverage, and exits `4` for a gating profile whatever the flags, since the content can force it. It is the honest outcome: the hunk was not read, and the review says so.
- **Saturation meets the same bound.** A reply that lists as many findings as it was asked for at most is split as a cut-off is, so decoys planted to saturate every part buy the same constant multiple. At the floor, or when `N` is `maxFindings`, the reply is read and the profile records a `findings-capped` gap, which gates as it did and is not lifted: a pull request can cause it with decoy findings.
- **What is left.** Splitting a part moves the boundary between what a model reads together, so a flaw that spans the two halves can be missed, as one that spans two parts can; the halves keep each file's header, never cut a hunk, and are balanced by tokens, not by risk.

### What quorum adapts by itself

Quorum lowers a provider's thinking and moves it to prompt mode by itself, for the rest of one review, when a reply shows it must: [What quorum adapts by itself](../20-using/20-configuration.md#what-quorum-adapts-by-itself) says when. What each trades, and what holds:

- **Thinking lowered** gives a shallower review of a part that needed more reasoning than the room allowed, where the alternative was a reply cut off before any answer. It happens only when `thinking` is automatic, so a level you set is never lowered; it is one progress line and one entry of `meta.adaptations`; a lowering the server refuses goes back to the server's own level; and a lowering moves only once the server shows it took the request, so a failure before it read the request (a network error, a 429, a 500 or a 503 after a cut-off) moves nothing and records nothing. Less reasoning can miss a subtle defect: set `thinking` to choose the level yourself.
- **Prompt mode** gives up the server's guarantee of well-formed JSON, so a weak model's reply is unreadable more often: a gap or a failed vote, never a pass. It gives up no structural control: under an enforced JSON mode a planted early close ends the generation with nothing trailing, where in prompt mode the model's continuation is written and the trailing-text rule refuses it ([Strict single-object parsing](#strict-single-object-parsing)). It never starts from `schema`, whose strict schema with the verdict first is what keeps a forced verdict from flipping a vote, nor from a mode you set. It happens for a finder or a voter, each its own entry, and shown.
- **Planted text cannot multiply the spend.** A provider's setting is probed once per review, so planted text that forces a cut-off or an empty reply costs the probe, and at most `concurrency` calls sent once more per setting: the calls already in flight at the old setting, each once. Every re-send is reserved by the token cap and stopped by the review's deadline like any attempt, and a probe the cap or the deadline stops moves nothing.
- **A vote's retry** with thinking lowered is the same vote request, so no text of a cut reply, or of another vote, reaches a voter ([Blind votes and arithmetic confidence](#blind-votes-and-arithmetic-confidence)).
- **Every line and field is code words** and a provider's id, never a word a server or a model wrote. A 400's body is matched against the structured-output field's name as a whole word and never quoted; a body that names `format` on Ollama, a word an unrelated body may hold, costs one probe.

### Saved state

`--state <dir>` keeps every answered call in a directory and reuses it on a rerun: [Saved state](../20-using/20-configuration.md#saved-state). A stored reply is read as the provider's own answer, so whoever can write the directory writes a part's review, a clean one included. That makes the directory a channel the other controls do not cover, and these are its:

- **Whose directory it is.** It is refused, before any call and with exit `2`, when it is a symbolic link or no directory; when another user owns it or its group or others may write it; when its real path, or any parent's, holds a `.git` entry, since a pull request writes its checkout and could plant a stored reply there; and when it holds files but no marker quorum wrote (`quorum-state.json`). It is made with mode `0700` when it is missing, and its files with `0600`. It is never offered under `quorum mcp`, whose calling agent could write it, and the bench, whose trials must each call the model, never uses one. No default directory exists, and no variable names one, so quorum writes nothing nobody asked for. On Windows the owner and mode checks do not apply: keep the directory in the user's profile.
- **Reads are untrusted.** An entry is read as a regular file, never through a link, under 8 MiB, through a strict schema (version, key, a text of at most 1 000 000 characters, a model of at most 256, the usage as counts), and anything else is a miss with one warning line. A stored reply is then checked as a fresh one: a research reply's envelope, and each finding against the whole diff; a vote's parse. A reply that fails is a miss, with one line, since it was saved only once checked and so was written by something else. A stored reply is never a verdict by itself: it enters the review where a fresh reply does.
- **A marker can only add work.** A cut-off or saturated reply is saved as a marker that holds what it lacked and never a text, and a rerun that finds it sends the part to recovery under the same bounds. A marker makes nothing read as clean, and a forged one costs a split, never a pass.
- **Entries are keyed by what was sent.** The key holds the request's content, its reply budget, the thinking level and the mode it was sent with, quorum's version and the provider's settings, hashed, never the request's bytes, which differ by a nonce, and never a credential: a settings form that holds one (a header kept as a credential) is only ever hashed, with the request. A reply made at a lowered thinking level is never taken for the default level's, and each send of a call has an entry of its own.
- **A reused reply costs nothing and counts for nothing about a provider.** It reserves nothing under the token cap, adds no usage, and tells the provider-down rule nothing, so it neither resets nor builds a count; a provider found down is called no more and its stored replies are not read either.
- **Writes never fail the review.** A write that fails is one warning line. Every line holds a code word or a number, never a reply's text, a key or a path.
- **What is left.** Whoever can write the directory writes the review: the docs say so, and say to remove it once the review it serves is done and never to restore it from a cache another job can write. A provider whose model changed under the same name reuses the old reply until the directory is removed. The directory grows by one file for each distinct request and is never pruned. A backup or a shared cache of it discloses the diff and the model's text.

### Content the diff does not carry

A diff can hide a file's change behind one line. A pull request that adds `src/a.js -diff` to `.gitattributes` makes `git diff`, run in its checkout, print `Binary files a/src/a.js and b/src/a.js differ` and none of the change. One NUL byte near the start of the file does the same with no attribute at all. A submodule's bump shows a commit and none of its code, and an `ignore = all` the pull request adds to `.gitmodules` hides the bump altogether. A model handed that section reads one line, finds nothing, and the review would pass with the file unread.

- **Such a file is a gap.** quorum reads git's markers by code, section by section: the `Binary files … differ` line, a `GIT binary patch`, the `Subproject commit` lines and a header of mode `160000`, and the `Submodule` line of git's `log` and `diff` formats. It lists the file in `meta.leftOut`, and every profile records a `binary` or `submodule` gap, which no flag lifts for a gating profile: exit `4`, even with `--allow-incomplete`. The section still reaches the models. A line of the same form elsewhere counts too, such as a commit message's: a gap it should not have stops the review for a person, where a missed one would pass a change unread.
- **The CI diff reads the base branch's attributes.** The recipe makes the diff with `git --attr-source=<base> diff --no-textconv --no-ext-diff --no-color --submodule=short --ignore-submodules=none <base>...HEAD`, so the change's own `.gitattributes`, text converters and external diff programs have no effect, nor does an `ignore` setting it writes in `.gitmodules`, and each submodule is a section of its own: [Using it in CI](../20-using/10-cli.md#using-it-in-ci). `--range <base>...<head>` makes that diff with those pins, and the others of [Git, run by quorum](#git-run-by-quorum). What is left is what is binary under the base branch's attributes, a file with a NUL byte near its start or one the base branch marks `-diff`, which is still a gap. A diff made without `--ignore-submodules=none`, such as a plain `git diff` of a branch someone else wrote, can leave a submodule out with no line at all, which quorum cannot list.
- **Content stored outside git is not detected.** A Git LFS pointer, or any file a `filter=` driver replaces at checkout, shows in the diff as the few lines git stores, for LFS a `version https://git-lfs.github.com/spec/v1` line, an `oid` and a `size`, while the content they stand for comes from elsewhere when the merged change is checked out. quorum reads those lines as text and lists no gap. A path review skips such a pointer and lists it as `skipped` with the rule `lfs`: it is under 1024 bytes of printable ASCII and exactly the lines of the spec, so it holds no code, and the content it stands for stays unread. A pull request can send a file of its own through LFS with one `.gitattributes` line, which the CI diff does not apply but a checkout after the merge does: review by hand a change to `.gitattributes` that adds a `filter=`.
- **No attribute or content excludes a file.** Only the config a run names can, through `exclude`, and each file it leaves out is listed, never dropped: no `.gitattributes`, `linguist-*` attribute or file content is read as an exclude, since a pull request writes all three. A pull request can still add a file where a pattern matches, so each pattern stays as narrow as the files it names: [Excludes](../20-using/20-configuration.md#excludes).

### Secrets held back

A change can hold a secret: a `.env` committed by mistake, a key pasted into a source file, a private key in a fixture. The model path has no secret of its own, but the diff is what the configured models are sent, and some are hosted, so quorum would hand a change's own secret to a third party, and into whatever that party keeps. So every diff, from every source, is read by code before any model sees a line, and a file that reads as a secret is held back whole: [Files held back as secrets](../20-using/15-sources.md#files-held-back-as-secrets).

- **What is held.** A file whose name is a secret's, such as `.env` or `id_ed25519`, or that ends in `.pem` or `.key`, in any case, or a file with a line that holds a credential quorum recognizes: a private key's armor and its body, and the keys of AWS, GitHub, Slack, Google, Stripe, Anthropic and OpenAI, with gitleaks 8.30.1's patterns and entropy floors, so a placeholder is sent: [The rules of a hold](../95-reference/20-json-result.md#the-rules-of-a-hold). A template, a `.env.example` or a Helm chart's `templates/secrets.yaml`, holds no value by its name and is sent, unless it holds a credential.
- **It is a gap, and why.** `meta.leftOut` lists the file as `secret` with its `rule`, a `secret-file` flag says why, and every profile records a `secret` gap, exit `4` for a gating profile, whatever the flags. A held file is code that no model read, and a pull request chooses its names and its lines: a change that names its file `credentials`, or puts one key-shaped line in it, would otherwise keep that file from the review and pass. As with a binary file, the change can hide its code this way, and the run cannot pass. A hit on one line holds the whole file, every section of it: quorum redacts no line, so nothing of a file that holds a key is sent. A diff whose every file is held calls no model and exits `4`.
- **A deletion of a file named as a secret adds no code.** A change that deletes such a file whole lists it as `deleted-secret`, with its flag and no gap: a `.env` holds values, and no code a review would read. The flag says that the history still holds the file, so rotate what it held. Only a section git writes for a whole deletion counts: a truncation to empty, a deletion with a context or added line, a `---` line that names another file than the header does, a series that edits the file and then deletes it, and a binary patch are held as a gap, never passed as one.
- **A deletion of code is a gap.** A file held for a credential in it, not by its name, may be code, and a deletion removes code as an edit changes it: a pull request that deletes `src/authz.ts`, with one key-shaped line in it, would otherwise pass with exit `0` and a flag, and no model would have read the check it removed. So it is listed as `secret` with its kind and is a gap, whatever the section looks like, and holding an edit of it is the same rule.
- **The reading is generous, and fails closed.** Every path a file's section names counts, its header, which is also read word by word so that a forged one still names the `.env` it spells, its `---` and `+++` lines and its `rename` and `copy` lines, so a rename under `-M` is held by its old name. Every line counts, removed and context lines included, so a commit that removes a key from a file holds the file. A hunk row that reads like one of those lines names a path too. The sections of one path are one file. The text no header names is the file of the empty name, held as one, which no `send` can name.
- **What remains.**
  - **A secret the rule does not know** is sent: a password in a URL, a key of a provider that gitleaks' patterns for the seven do not cover, a value in a file with an ordinary name.
  - **A moved secret.** Under `--no-renames`, the form quorum's own sources use, a `.env` moved to `config.txt` is a deletion of `.env`, listed `deleted-secret`, and a new `config.txt`, which is sent unless its content holds a credential the rule recognizes.
  - **A deleted file's lines.** A change that deletes whole a file held by its name passes with no gap and sends none of it. That holds even for a `.npmrc`, whose lines can be install settings (`ignore-scripts`, a scoped registry) as well as tokens, so such a deletion is reviewed by no model, only flagged: a person looks at the flag.
  - **Retention.** A provider keeps what it was sent for about 30 days, and flagged content for up to two years at Anthropic, so a key that reached a model is to be rotated, and the hold is a control only for what it recognizes.
  - **The override is the operator's.** `--send <path>` on the command line and the config's `send` name a file to send all the same, by the path as the `left out:` line prints it and `meta.leftOut` lists it, matched exactly, and a file named is neither held, listed nor flagged. Both come from the person who runs quorum, or the config a job names from the base branch, and never from the change: no file, attribute or message of it is read as a `send`, so a pull request cannot lift the hold on its own file. A provider then receives the file, and keeps it as any other: [Sending a held file](../20-using/20-configuration.md#sending-a-held-file), [`review`](../95-reference/30-library-api.md#review) for a program.

### Git, run by quorum

A repository someone else made holds what its author wrote. Its config can name a program as a file-system monitor, a pager, an external diff, a text converter or a filter, its attributes can send files to them, its hooks directory can be its own, a bare repository can sit in its tree, a replace ref can swap one object for another, and a revision typed after a flag is read as an option. A plain `git diff` there can run any of that, with the job's rights. So quorum runs git itself, in one place, and never through a shell: [How quorum runs git](../20-using/15-sources.md#how-quorum-runs-git).

- **The plumbing set.** A range runs `rev-parse`, `merge-base` and `diff` of two commits, which read objects by id, and the checks that open the repository. A path review adds `ls-tree` of a commit and one `cat-file --batch`, which list and read objects by id. The local sources add `diff` of the index and of the working tree, `config` and `ls-files`, which read the index and the working tree: with the file-system monitor pinned off they run no monitor, but a working-tree diff runs a clean filter whatever `--no-ext-diff` and `--no-textconv` say, which the next bullet answers.
- **The pins and the allowlist.** Every call carries the pins, and its child gets an allowlist of the environment and not the parent's: no `GIT_DIFF_OPTS`, `GIT_EXTERNAL_DIFF`, `GIT_CONFIG_PARAMETERS` or key. The prototype tried them on git 2.50.1 against a repository built to be hostile. Its `.git/config` named a marker program as `core.fsmonitor`, `diff.external`, a text converter, a driver's command, the three programs of a filter, `core.pager`, `pager.diff` and a hooks path, and set `diff.algorithm`, `diff.context`, `diff.renames`, `core.abbrev`, `core.quotePath` and a dozen other settings that reshape a diff. Its `.gitattributes` and `info/attributes` sent every file to the driver and the filter, and the parent's environment held `GIT_DIFF_OPTS` and `GIT_EXTERNAL_DIFF`. Unpinned, git ran the monitor, the filter's process and the driver's command. With the pins every call of the set ran nothing, a replace ref was read past, a bare repository committed in the tree was refused, a partial clone fetched nothing, and a range's bytes equalled those of a clean clone, which a test of the real git holds.
- **The local sources run the repository's filters, unless the trust check refuses them.** `--local` runs the working-tree diff, which runs the clean and process filters an attribute names: with every pin set, the prototype's hostile repository ran its filter's `process` program six times, and a repository's own config can name any program there. So both `--local` and `--staged` read the filter keys with their scope first (`config --show-scope -z`, which reports an included file's keys under the scope of the file that includes it) and refuse the source, exit `2`, when any key's scope is not `system` or `global`, whatever its value: [Trust](../20-using/15-sources.md#trust). `--trust-repo-config` says the repository is the user's, and is the one way to run its filters. What remains is the user's own global and system filters, which run as they do with their own git, and an attribute the repository sends a file to them with, read from `HEAD`'s tree and never the working tree's.
- **Untracked files are read by quorum, not by git.** `--local` lists them with `ls-files`, which never follows a link, then reads each one itself: a name that is not UTF-8, one with a `..` segment or a leading `/`, one whose parent directory's real path is not the real top level joined with it, and anything that is neither a regular file nor a link is refused, and a regular file is opened without following a link. A link is written as its target and never read through, a nested repository as a gitlink and never entered, and a file `exclude` matches is listed and never opened. A link or a FIFO swapped in after the listing is refused too. The plan's checks word the common cases, and the read decides: on macOS the file is opened on its real path with `O_NOFOLLOW_ANY`, which refuses a link in any part of the path in the one `open`, once a first check shows the kernel honours the flag; on Linux it is opened through a handle of its parent directory, once `/proc/self/fd` shows that handle is that directory of the real top level. So a process that swaps a parent for a link at any moment, between the checks or at the open, gets the swap refused as a change, and no file outside the tree is read. On another platform an untracked file is refused, and so is one where the system cannot show that it refuses a link. What remains: on macOS a link's target is read with `readlink` of its path, which has no such flag, so a process that swaps a parent at that instant makes quorum write the target text of a link outside the tree, never a file's bytes; a hard link in the tree is a regular file to quorum, as it is to git, which commits its content; and on macOS a user mounts a disk image or a share in the tree with no privilege, and a mount point is no link, so neither mechanism refuses what it holds. On Linux a `/proc` an attacker mounted, or a bind mount over a directory of the tree, needs privileges this model does not give the attacker.
- **A path review reads a commit's objects, never the working tree.** It lists the commit's tree and reads each blob by its id, so an edit that is not committed, a link in the work tree and an attribute file of the checkout are never read, and nothing in the work tree can change what a review sees of the commit. That holds for objects git fetched itself, which it checked as it stored them. It does not hold for a `.git` someone handed you, whose objects git does not re-hash on read: the last bullet below says what that costs.
- **A revision is never an option.** The one string git gets from a user is a revision, once, after `--end-of-options`; it is refused before git when it is empty or starts with `-`, and every other argument is a full id git printed, checked first. Written as a `diff` revision, `--output=<file>` wrote a file; as a resolved one it is refused. Every `diff` ends with `--`, so a tracked file named like a commit id is no revision either. No message repeats a revision as typed.
- **The floor.** Git 2.41 or later: `--attr-source`, which makes the base commit's attributes the ones that count, came with it, and every other pinned option is older. An older git, none on `PATH` and a git whose version cannot be read exit `2` before it reads anything.
- **What remains.**
  - **The sinks are open-ended.** Git has many settings that run a program, and a release can add one. The pins close the known ones and the set of commands keeps the rest out of reach, but a pin set is a floor, not a guarantee. Run quorum where a stranger's program has little to read, in a clone you made, and keep the `git` on `PATH` out of a pull request's reach.
  - **A `.git` someone handed you is no proof.** Git does not re-hash an object when it reads it, so a handed-over object store is not proof of its objects. Nor is it proof of where it points: a `.git` file can name another repository's git directory on the machine, as a linked worktree's does, and `objects/info/alternates` borrows another repository's objects, as a shared clone's does, so a review would then send that repository's files to the configured models. Quorum refuses a `core.worktree` that names another repository, and cannot tell these two cases from a linked worktree or a shared clone. A handed-over `.git`'s `info/attributes` can mark files `-diff`, which the review then lists as binary gaps: it runs nothing and fails closed, and no switch turns that file off. Its commit-graph file can skew the merge base, which `merge-base` trusts for parents. So review commits fetched from their origin, in a clone you made.

### Paths, never handed to git

A path review takes paths from the user, and a path is where a pathspec or a revision can hide: a `:(top)` or `:(attr:...)` magic, a glob, a name that starts with `-`. So no path a user wrote reaches git. What git is given is the commit, resolved once as a revision of `--range` is, and ids it printed.

- **Listed once, filtered in code.** `ls-tree -r -z --long` of the commit's id lists every entry. Quorum decodes each name as a diff would read it back and keeps the entries a selection names, so no pathspec magic applies, and git has no path to read as a pathspec (`--literal-pathspecs` is pinned all the same). A kept blob is read by its id through one `cat-file --batch`, never by `<rev>:<path>`. A selection whose listed sizes pass 16 MiB is refused before any blob is read.
- **Contained.** A value that is empty or absolute is refused before any git, one that leaves the top level of the repository is refused once the working directory's place in it is known, and each value must match a tracked file. The working tree is never opened, so no link is followed: a link in the tree is a blob that holds its target, written as mode `120000` and never read through.
- **The skips are listed, never hidden.** Each file a path review skips is in `meta.leftOut` with its rule, and a skipped secret, by its name or by a credential in its text, raises a flag: a person sees what went unread. `--no-default-skips` turns off the vendored, lockfile, minified, test and binary skips, so an operator who does not trust the lists can have those files read. A secret stays skipped under it, as do a gitlink and a Git LFS pointer, and only the operator's `--send` or `send` sends one: the hold on every diff would turn a secret the review sent into a gap anyway. A skip is no gap, which is what lets a codebase review finish; the price is that a file that fits a rule goes unread.
- **Nothing is read from the tree's own attributes.** A `.gitattributes` the change writes, `linguist-vendored`, `linguist-generated` or `-diff`, skips nothing, since an author would choose what is unread. A tree can still shape a file to match a rule, a name under `vendor/`, a `.min.js` suffix, a NUL byte or long lines, and the file is then skipped and listed. The default skips choose what is unread by code, from a fixed list, never from the change's text: [What a path review skips](../20-using/15-sources.md#what-a-path-review-skips).

### Unreviewed and incomplete reviews

A discard never rests on a failed vote: a finding that a failed vote could still have kept is `unreviewed`. A finding the harness could not read, a kept finding whose failed votes could have raised it to a higher level, a research reply whose findings were all unusable, findings beyond the cap, a request its provider refused as too large for its model, a hunk too large for any research request of its model (`too-large`), a research part that failed (`research-failed`), a part or vote that a provider found down was never sent (`provider-down`), work the review's token cap (`token-cap`) or its deadline (`review-deadline`) stopped, a file whose change the diff does not carry, binary or a submodule's commit, and a file held back as a secret (`secret`), are recorded in `meta.incomplete`. Either makes the review incomplete, so the CLI never exits `0` for a gap of a gating profile that the harness detects: it exits `4`, or `1` when a gating profile also kept a finding at or above its fail-on level, `high` by default. Two choices lift the `4` to `0`: a profile with `failOn: none` in the config, and `--allow-incomplete` in the command, which lifts a gating profile's gaps only when each is an unreviewed finding or a `vote-failed` gap, and every failed vote behind them failed in passing: a dropped connection, a timeout of its own, or an HTTP 408, 409, 429 or 5xx. That is what the vote's recorded `failure` says ([A vote](../95-reference/20-json-result.md#a-vote)). A pull request causes every other gap directly: by padding one hunk until no request of the window holds it, with decoy findings that push a real one past `maxFindings`, with decoy findings and drawn-out replies that spend the review's token cap or hold it until its deadline, with text that breaks the finder's reply, which is that part's `research-failed` gap, with one `.gitattributes` line or one NUL byte, with a file named `.env` or one line that reads as a key, or with text that a voter refuses, that cuts its reply off or that leaves it unusable. So no flag lifts them, and a reason a later version adds is out of the flag's reach by default. The gap stays in the result either way.

- **What stays.** A reply that planted text drew out can still end in a lifted failure, a timeout of its own or a gateway's 504, so a gating profile does not use the flag on a change its operator does not trust.
- **A failed part is a gap no flag lifts.** A research call that fails, or whose reply is no findings envelope, is its profile's `research-failed` gap, a gating profile's included: the part of the change it held went unreviewed, and `--allow-incomplete` lifts it no more than it lifts a hunk no request holds. The review keeps what the other parts read and exits `4`.
- **A provider that is down is called no more.** Three calls of one provider in a row that fail for a reason of its own (`network`, `http`, `timeout`, `process`, `unsupported`, `invalid-response` or `no-answer`, counted across every profile and role that shares it) end its calls for the review: the calls in flight run to their end, and the parts and votes it was never sent are `provider-down` gaps, exit `4`, never a pass. A reply that came back resets the count, and a refusal, a reply cut off, a request refused as too large or a limit never counts, so a pull request cannot take a provider out of the review with text a model refuses. What remains is a failure the server shapes by content: a content filter that answers an HTTP 400 to a request holding some text, or reasoning inflated past `timeoutMs`, can end the calls to a provider early, and so can planted text that makes the model reply with nothing, or only reason, which also counts toward the provider being down, a third way the reviewed content can end a provider's calls; it fails closed. The residue is a gap, `provider-down` and exit `4`, and the review rejects, exit `3`, only when no research call answered: a pull request can make a review fail to read, never read as clean. A reply whose own code says the account's credit, quota or spend limit is used up finds its provider down at its first failure, not its third, so a server's body can stop its own provider at once by naming a quota code, as it can by failing; it can stop that provider alone, the codes are matched and never quoted, and the review keeps what it read.
- **What it costs.** A vote whose reply was unusable, the usual failure of a weak local voter, is no longer lifted: give such a voter JSON mode or a stronger model ([Structured output](../20-using/30-providers.md#structured-output)).
- **A skip is listed, and is no gap.** A file a path review skips, as vendored, a lockfile, minified, a test, a secret (by its name or by a credential in its text), binary, a gitlink or a Git LFS pointer, is in `meta.leftOut` with the rule that took it, so a person sees what went unread, and the review is not incomplete for it. A skipped secret also raises a flag, and stays skipped under `--no-default-skips`, which only `--send` and `send` override: [Paths, never handed to git](#paths-never-handed-to-git).
- **A path review over a cap is refused before it reads or calls.** A selection whose listed files pass 16 MiB exits `2` before any blob is read, and one whose research may pass `maxReviewTokens` exits `2` before any call, after printing its estimate. `--large` runs it all the same and reviews what the cap allows: the parts the cap cannot fund are a `token-cap` gap, exit `4`, which no flag lifts, so a tree too large for the cap is never read as a clean review: [What a path review costs](../20-using/15-sources.md#what-a-path-review-costs).
- **An empty selection is an error, and an empty change is not.** A path selection whose every file is left out exits `2`, since a review that read nothing must not pass. A diff, a range or the local changes with nothing in them is `nothing to review`, exit `0`: there is no change to be wrong about.

### Advisory flags

The harness reads the added lines and the file names of the diff by code, before any model sees them, and flags hidden characters and text addressed to an AI reviewer. It also flags, as `secret-file`, a file held back as a secret, by its name or a credential it holds, and one a path review skipped as a secret, read from the files left out and not from the diff's lines, and it quotes no line of the file. A flag appears in `meta.flags`, in a `flag` event and in a `flag:` line on stderr, and it is never a gate: it changes no verdict, gap or exit code. It tells a human where to look, and it is not a defense: [Advisory flags](./30-output-handling.md#advisory-flags).

### Inert output

The CLI writes nothing that a terminal or a GitHub Actions runner would act on, and shows or escapes every hidden character of the class in the text it carries. Every line of stderr that carries text from outside the CLI passes through `inertLine`, which shows each hidden character as `<U+XXXX>` and breaks the forms of a GitHub Actions workflow command, and stdout is written by the reporter `--format` names: `inertJson` for the JSON result, which escapes them and parses back to the same data, and `inertLine` for each line of the text and brief reports, with color only around words quorum wrote. The `--output` files hold the same reports through the same reporters, never colored, each written whole by a rename that never writes through a link at the path itself, though the directories of the path are followed. `quorum bench` prints its report, or its plan with `--dry-run`, on stdout through `inertLine`, and writes `results.jsonl` as one `inertJsonLine` per record, `run.json` and `report.json` through `inertJson` and `report.md` through `inertLine`, only inside `--out`, which it makes with its missing parents, its two data files readable by their owner only, and never through a symbolic link. [What the CLI writes](./30-output-handling.md#what-the-cli-writes) has the details and the limits.

The Markdown reporters, which write for a place GitHub renders, the summary of `-f markdown` and the line comments that `-f payload` adds to it, follow one rule: text a model or the diff wrote appears in their output only in a code span or a fenced block whose fence code computes, longer than any backtick run inside, so no mention, reference, link, image, HTML or line break of that text acts, and never in a table cell. Their own words hold no `$`, so no span of theirs sits between two, which GitHub reads as math. The library exports `codeSpan`, `fencedBlock` and `inertPlain`, which a program that writes Markdown or plain text a viewer may link, such as a SARIF message, calls itself: `inertPlain` breaks an `@` that no ASCII letter, digit or `_` precedes, a `#` before a digit and `://`, and caps the text: [Printing a review yourself](./30-output-handling.md#printing-a-review-yourself).

| Channel | Threat | Control | What remains |
| --- | --- | --- | --- |
| GitHub Markdown | Mentions, references, images, links, HTML, suggestion blocks and a forged marker in the summary | Code spans and computed fences for every text of a model or the diff, no image and no link, the marker on the first line only and every line through `inertLine`; a program that finds the summary by its marker checks the comment's author too | GitHub's real allowlist is unpublished, so the guarantee rests on the code span CommonMark defines, which GitHub's renderer follows |
| SARIF | A mention, an issue reference or a URL in an alert's message, which GitHub may link, and a file name that breaks the upload or names another place | `inertPlain` on every text a model or the diff wrote in a message, which breaks an `@` that no ASCII letter, digit or `_` precedes, a `#` before a digit and `://` and caps it at 1,000 code points; no URL but `informationUri` and `$schema`; a path as a relative URI, well formed and percent-encoded segment by segment, and no location, of a result or of a notification, for a path that is not a clean relative path (a leading `/`, an empty, `.` or `..` segment), which is counted instead | Whether GitHub links a message's URL at all is not documented, so the rule is a precaution; a finding can still make an alert's text misleading, as any claim of a model can |

### A saved result as input

The post job of a two-job workflow renders a result another job wrote, and that job ran on a pull request, so the file is the input of an attacker's run and not a record of what quorum did. `quorum report` and `readResult` treat it so. The reader takes at most 256 MiB, counted in bytes, and parses it with `JSON.parse`, which runs nothing. It refuses a result of another release before it reads the shape, and then holds every object to a strict schema: an unknown key anywhere, a value outside a closed list, a profile id that is no code word, a finding of a profile the result does not hold, a text over the cap the harness keeps to, and a public view that still carries what the view withholds are each refused, so the reporters only ever see the values quorum writes. Each refusal is one message with no value and no text of the file and no key but a code word, and exit `2`: the post job fails, it never renders something it did not understand. It runs no model, reads no config and runs no git, so the file can name nothing to run or to fetch.

What remains is that the schema checks the form of a result, never that a review wrote it. A result a pull request's own job wrote proves nothing about the code: its author can write one with no finding, or with a verdict of its choosing, and the post job will render it. So the review job's exit code is the gate, and no decision rests on a rendered result alone. Sub-project 4, which acts on a review, takes no verdict from a saved result for the same reason.

### The CI workflow

The reference workflow of [Reports for GitHub](../20-using/80-reports.md#a-github-workflow) splits a pull request's review into two jobs, so no job holds both a secret and the pull request's code.

| Job | Holds | Does not hold |
| --- | --- | --- |
| Review | The model key and `contents: read` | A checkout of the pull request's head, a write token, any other permission |
| Post | `security-events: write`, `actions: read` and `contents: read` | The model key, a checkout, a model's call |

- **The review job checks out the base commit,** with its history and without leaving a token in the checkout. No checkout of the head exists, so the config file and any file the job reads are the base's, and `--range` reads the head's commits with the plumbing set alone, which brings no config, hook or attribute of the pull request: [Git, run by quorum](#git-run-by-quorum). It writes the public view to `$RUNNER_TEMP`, a directory the pull request cannot plant a file in.
- **The post job runs nothing a model wrote.** It reads the saved result through the strict reader and renders it, so a result that is not one quorum wrote fails the job: [A saved result as input](#a-saved-result-as-input). What it renders proves nothing about the code, so the review job's exit code is the gate.
- **A fork's pull request runs neither job.** The review job's `if` skips it, so a fork's code never meets the model key, and the workflow does not use `pull_request_target`. A maintainer reviews a fork by hand: [A pull request from a fork](../20-using/15-sources.md#a-pull-request-from-a-fork).
- **Every value reaches a script through `env:`,** never as a `${{ }}` expression inside a `run:`, so no ref, id or variable is parsed as shell code.
- **Workflow commands.** The runner reads a line of a log that starts with `::`, or holds `##[`, as a command, which a claim copied into the log could use to add an annotation or mask text. Quorum writes none of its own, and every line it writes that carries text from outside passes `inertLine`, which breaks both forms, so the log, public on a public repository, holds no command an attacker started: [Inert output](#inert-output).

### The public view

On a public repository, a pull request's comments and code scanning alerts are readable by anyone who can see it, and the job summary and the artifact of the review job by anyone signed in. The author of a change is a reader of all of them, and a review of an author's text that publishes its reasoning, its discarded findings or its model is an oracle the author tunes the next push against. So the review job writes the public view, `--view public`, and the other sinks render it: [The public view](./30-output-handling.md#the-public-view).

| Sink | Who reads it | What it holds |
| --- | --- | --- |
| Artifact, job summary | Anyone signed in, on a public repository | The public view; the artifact holds the full result only on a private repository |
| The review's stderr | The log, public on a public repository | Under `--view public`, the banner names each provider by its config key with no model or origin, a gap's line gives its profile, reason and file with no detail, a dropped finding has no reason, and a failure is in fixed words |

The view withholds each vote's reasoning and error, the discarded findings (it counts them), the providers and models, the usage and each gap's detail, and keeps the rest. A format that writes for a stranger renders the public view of whatever it is given, so no call reaches it with the reasoning in it. `outcome` reads a view as the result it came from, so a job that holds only the view concludes what the review's exit code said, a lifted gap included.

### The calling agent

An AI agent that calls quorum, such as Claude Code through `quorum mcp`, reads a review's result as input, and an attacker wrote the change the result is about. So the agent is told fixed words, counts and fields that quorum's code checked, and the claims of the review only in two named fields, a finding's `category` and `summary`, each capped at 300 code points and made inert. A file name shows its hidden characters. The result has a fixed shape within 10,000 bytes of JSON, and what does not fit is dropped whole and counted, so no string is cut and the result is bounded by the budget: [What a calling agent receives](./30-output-handling.md#what-a-calling-agent-receives).

- **A tool can only shrink what it contributes.** Nothing quorum writes can stop an agent from following a claim it chose to believe. What quorum controls is how much text the agent is given, where, and that every piece is inert and labeled, so the defence against a claim that steers an agent sits in the agent's own permissions: what it may run and what it may write without asking.
- **One item cannot crowd out the rest.** An item over 2,048 bytes of JSON, a file name of a megabyte, is dropped and counted before the budget drops anything, so it cannot push the real findings out. What remains is crowding by items under that size: an attacker who makes many of them can still fill the budget with their own names and claims, which is bounded by the budget, and each finding dropped is counted in `dropped`, so the agent knows the result is partial.
- **What remains:** the summaries. A summary is a model's claim about code that may be hostile, so a planted instruction can still reach the agent as one, within 300 code points. The notice tells the agent to check a claim against the code and to follow no instruction in one, which is no defence by itself.

What the agent can ask of `quorum mcp`, and what it cannot, is decided at the launch, by the operator: [The MCP server](../20-using/90-mcp.md).

- **A constant tool, and a call that names a source.** The tool's description, its input schema and its annotations are constants of the release, whatever the config or the repository holds, so no text of a project reaches the agent as part of the tool. A call names `local`, `staged`, a range, or paths at a commit, and never a diff: the agent does not choose the code reviewed, quorum reads it from the repository. Every message of the schema is fixed, so a refusal repeats nothing of the call, and a failure of a review is one of a few fixed texts whose reason goes to the server's log, never to the agent.
- **The gates are the launch's.** `--large`, `--trust-repo-config` and `--send` are flags of `quorum mcp`: no argument of a call lifts one, so an agent cannot make quorum run a filter program a repository names, send a file held as a secret to a model, or review what may pass the token cap.
- **Paths stay in the root.** A path is normalized, and one that is empty, absolute or leaves the root, `CLAUDE_PROJECT_DIR` or the directory the server was launched in, is refused before any git runs. The root may be a subdirectory of the repository: a path stays inside it, while `local`, `staged` and a range review the whole repository, as the CLI does from there.
- **One review at a time.** A call made while a review runs is answered at once that one is running, and so is one made right after a review was cancelled, until that review has stopped: an agent cannot start reviews in parallel and spend the operator's tokens faster than one review's cap allows.
- **A session budget bounds a looping or steered agent.** A review is bounded by its token cap, and the server by `--max-session-tokens`, four times the cap by default: each provider call's spent tokens count, and a review that ends without a result, cancelled, aborted or failed, is charged its whole cap, since no call is reported once a review is aborted. A call starts only while a whole review's cap fits in what is left, so an agent that calls again and again, or cancels each review to start the next, stops at the budget: [Limits](../20-using/90-mcp.md#limits).
- **`--code-fields-only` leaves no model text for the agent.** Without a category and a summary, the result holds fields quorum's code checked and nothing a model wrote about code that may be hostile. It is the strongest control a tool has against a claim that steers an agent, and the operator's to set at the launch.
- **`--require-approval` is a hint a client may ignore.** It asks Claude Code to have the person approve every call, even in its auto modes. Quorum cannot make a client ask, so the defence stays in the person's permissions and in the budget.
- **The config is outside the project.** The agent can write inside the root, so a config there could set `send`, a provider's endpoint or a prompt for the next launch. `quorum mcp` refuses a config whose path as named lies inside the root, through a link or not, whose real path does, or that is a link in the root that leads out, before it reads the file, so a code config's module never runs with the operator's keys in the environment. `profiles` in a call narrows among the profiles the launch resolved, from the config it read once, never from the file again.
- **Quorum's code and the SDK lie outside the project.** For the reason the config must, the agent can write inside the root, so a quorum or an SDK under a project's `node_modules` is code it can change, and the next launch runs it with the operator's keys and gates. Run `quorum mcp` from a global install or the release binary: [The MCP server](../20-using/90-mcp.md#starting-it). Quorum does not check where its own code lies, so this is the operator's to keep.
- **A repository's `.mcp.json` is not the way to start it.** Its command and flags are the repository's, and `claude -p`, the Agent SDK and cloud sessions load a project's servers without asking: a hostile repository would choose the flags, the gates included. Add the server to your own settings, `claude mcp add --scope user`.
- **The environment is the operator's.** The server reads the `QUORUM_*` variables of the environment Claude Code gives it, and a project's `.claude/settings*.json` `env` sets variables there once the folder is trusted: a provider's endpoint, the command of a `claude-code` provider or the token cap. The config's own placement does not cover that. The hook that reviews Claude's commits reads them the same way, since Claude Code runs it in that environment too: [A hook on Claude's commits](../90-recipes/20-claude-code.md#a-hook-on-claudes-commits). A project whose settings you have not read is not one to run `quorum mcp` or that hook in.

## What the harness cannot detect

Quorum cannot tell what a model read: it checks what the model answered, never what it saw of the prompt. An endpoint that truncates an oversized prompt answers all the same. Ollama's `/v1` cuts a prompt past the model's context length and still returns HTTP 200, so a review of what was left can come back clean, with exit `0`. So the CLI's built-in default speaks Ollama's native API, which is told the context size and, from Ollama 0.12.6, refuses an overflow, and quorum refuses to send what may not fit, by [the size guard](#the-size-guard), a bound that holds for the open tokenizers checked. What the guard cannot know remains:

- **A `contextTokens` above the server's real window.** Quorum trusts the number it is given and reads it from nowhere else. On Ollama's native API, the CLI's default, a server loads the `num_ctx` quorum sends, clamped to the model's trained context, so keep `contextTokens` at most what `ollama show <model>` reports. What remains is a base URL a user points at Ollama's `/v1`, which cannot be told its context, so a server that loaded less than you stated cuts a prompt in silence, or at another endpoint that cuts in silence. LM Studio loads less than its maximum, and an Azure deployment can differ from its model's documentation. State the window the server really gives: [Finding the number](../20-using/20-configuration.md#finding-the-number).
- **A tokenizer that takes more than one token per byte.** The bound holds for the byte-level BPE and byte-fallback SentencePiece tokenizers checked, and for one that normalizes with NFC, NFKC, NFD or NFKD first, since each code point counts at its longest form. It is not proven for a closed tokenizer (Claude, Gemini, Grok). Of the hosted vendors, Anthropic, Gemini and OpenAI refuse an oversized prompt with an error, and xAI's behaviour is not known. That refusal does less than the guard: on research it is a `research-failed` gap, exit `4` for a gating profile, and on a vote it is a failed vote with an HTTP 4xx status, which `--allow-incomplete` does not lift. A tokenizer that folds case is not covered either, which no chat model's is known to do. Through `claude-code`, Claude Code's own refusal of a prompt as too long is a `request-too-large` gap, unlike the hosted APIs' refusals above: no flag lifts it.
- **A server that adds more than 512 tokens around the messages**, such as the `TEMPLATE` or `SYSTEM` text of an Ollama Modelfile.
- **An Ollama older than 0.12.6.** It ignores `truncate: false` and `shift: false`, so even on its native API, the CLI's default, it cuts an oversized prompt in silence, and drops the start of a prompt to make room for a reply that fills the context: [`ollama`](../20-using/30-providers.md#ollama).
- **Text that `extraBody` adds** to a request, which the guard does not count, and a server-side switch that truncates the prompt, such as vLLM's `truncate_prompt_tokens` or OpenRouter's `transforms`, which the guard cannot see. The config is trusted, so quorum documents them and does not refuse them.
- **A provider object**, which checks its own requests: the guard lives in the shipped adapters.
- **A reply that outruns its reserve.** A server that shifts its context as the reply is written, such as Ollama's `/v1`, LM Studio's rolling window or llama.cpp's server with `--context-shift` on (it is off by default), can drop the start of a prompt to make room for a long reply: every adapter sends the request's reply budget, at most `maxTokens`, as the server's limit, which a server that honours it enforces. A thinking model's reasoning counts against that reserve, and a long or hard diff lengthens it, so no persuasion is needed. Ollama's native protocol, the built-in default's and the `ollama` preset's, closes it from Ollama 0.12.6: it sends `shift: false`, so a reply that fills the context stops as a truncation.

Beyond the guard, a job that reviews untrusted changes can bound the diff further before piping it in.

## Independence

Voters are blind to each other, so their reasoning is independent. Their errors are not statistically independent: one study put nine judges from seven model families at about 2.2 effective votes, and prompt, ordering or temperature variants did not help, so three lenses on one model are probably worth one or two votes. Blind voting is still right: voting captures most of the gain of debate, and avoids sycophancy between agents. The bench measures the lenses' error correlation, so a panel's effective votes are a number and not a guess: [The lenses' error correlation](./40-measurement.md#the-lenses-error-correlation).

- **A provider per lens is variance reduction, not a security measure.** Mixed model families helped in older studies, and nothing shows they stop a tuned attack.
- **Voting filters false positives only.** Recall rests on the finder, which reads the same poisoned diff, so the finder is a single point of failure for suppression: the panel cannot judge a finding that was never proposed.

## Model-written text is untrusted

A result, and each line of a bench's `results.jsonl` that holds one in full, carries text that models wrote, servers sent or the diff holds; a review whose research reply could not be used holds a `research-failed` gap, never the reply. Quorum stores it as it came, apart from some cleaning, and makes its own output inert. [Output handling](./30-output-handling.md#text-an-attacker-can-influence) has the fields, the cleaning and what a renderer must do.

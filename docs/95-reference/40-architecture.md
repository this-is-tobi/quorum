# Architecture

How the code is laid out, which module may depend on which, what happens in a review, how a release is built and published, and how the suite runs. For a reader who changes quorum, or wants to know where a behaviour lives before trusting it.

## Modules

| Module | Holds |
| --- | --- |
| `src/core/` | The core, with no access to the environment, the network, files or the process. `quorum.ts` is `createQuorum`: the input checks, the compiled profiles, and the review that runs them. `types.ts` holds the shared types, `ports.ts` the `Provider` port, `EventSink`, `ProfilePorts` and `QuorumPorts`, and `errors.ts` the error classes, `isSafeSegment` and `issuePath`, which build every issue path |
| `src/core/stages/` | The stages of one profile: `research.ts`, `dedup.ts`, `panel.ts`, and `context.ts`, which they share: the compiled profile, a call inside the concurrency limit, and the stage events |
| The rest of `src/core/` | `policy.ts`: the rules, thresholds, confidence and where a verdict lands. `profile.ts`: the profile checks and warnings. `prompts.ts`: templates, fences and the notices. `output.ts`: the strict parsing of replies. `diff.ts`: splitting a diff and locating a line in it. `verify.ts`: checking findings against the diff, and their evidence. `concurrency.ts`: the shared limiter. `sanitize.ts`: the hidden-character class, and the inert rendering of a line and of JSON. `flags.ts`: the advisory flags read from the diff |
| `src/profiles/` | Profiles, as data: `security.ts` |
| `src/providers/` | Adapters behind the `Provider` port, and what they share. `openai-compatible.ts`, `anthropic.ts`, `gemini.ts` and `ollama.ts` are the HTTP adapters, each with the reader of its replies, and `claude-code.ts` is the adapter that runs the user's `claude` CLI instead: its options and their checks, the command line, the child's environment and the reading of its JSON result as pure functions, then the process, a directory per request, the spawn, stdin, the output caps, the process group, abort and cleanup. `http.ts` is the request: no redirect is followed, reads are capped, every failure becomes a `ProviderError`, and the key, the base URL's path and the header values are redacted from what a server sends back. `options.ts` holds the shared options and their checks, under the rules each adapter declares: the body fields it writes, its tool fields, the fields that set its reply limit, the headers it always sends and its structured-output modes; and `prepareHttp`, which runs those checks, then the adapter's own, and builds what every request sends, the URL, the headers, the values to redact and a copy of `extraBody`. `presets.ts` holds the presets, frozen data. `build.ts` builds a provider from a spec that names a preset or a protocol, `claude-code` included, after the spec's checks and the adapter's, and hands a `claude-code` adapter the environment it is given; `resolve.ts` calls it to check each provider and `fromConfig` to build each one, and it is not exported from the package. `reply.ts` holds what the readers share: the failure, the token counts, the message of a reply that ended early, and the joined text of its parts. `messages.ts` places the system text, natively or inline. `size.ts` is the size guard every adapter runs before a request, with a reserve of its own for what the adapter adds (4096 tokens for `claude-code`): it bounds the request by one token per UTF-8 byte of its text (each code point at its longest form, as it is, decomposed or compatibility-decomposed), a reserve for the chat template and the reply budget, and refuses one that may not fit `contextTokens`. |
| `src/config/` | The config layer, which the CLI and `runQuorum` call through `loadConfig` and `fromConfig`: `src/index.ts` exports them with `defineConfig` and the types, and `scripts/schema.ts` calls the schema to write the JSON Schema. `schema.ts` holds the zod schemas of a config, strict at every level: the file variant, for YAML and JSON, which is data only, and the code variant, for TS and JS, where a provider may also hold its key or be an object implementing `Provider`; their types, `QuorumConfig` and `QuorumConfigFile`; the issues a parse reports, which repeat no value and print a key that is not a safe name as `*`; and the JSON Schema of the file variant. `load.ts` is `readConfigFile`, which reads one named file into a checked config: a regular file of at most 1 MiB in UTF-8, holding YAML 1.2 of the core schema, which refuses an unknown tag, a YAML 1.1 tag such as `!!binary`, an alias and a repeated key; JSON, which refuses a repeated key; or a module whose default export is the config. Its value must be plain data, a provider object aside, with no `__proto__` key, and at most 10000 values; then the schema checks it, and every prompt file it names is read once, however many profiles name it: at most 64 KiB each and 1 MiB in all. A prompt path is read as given, relative to the config file or absolute, and is not confined to its directory: a config is trusted like code. `env.ts` reads the `QUORUM_*` variables, their deprecated aliases and the voter they derive, which never carries a key or a model to another origin. `profiles.ts` resolves the profiles that run, each from a built-in profile or its own fields. `resolve.ts` layers a config with the environment and the built-in defaults, binds the roles, reads the keys and the `claude` executable of each `claude-code` provider a profile uses, and checks every provider with the builder, and returns the frozen resolved config. `claude-code.ts` finds that executable: `QUORUM_CLAUDE_CODE_COMMAND`, else a code config's `command`, else `claude`, looked up in the absolute entries of `PATH` only, and holds the billing warning of a key that Claude Code would bill. `from-config.ts` is `fromConfig`, which checks a program's config as a code config is checked, builds each provider and wraps each provider object under its config key; `loadConfig`, in `load.ts`, reads the file `configPath` or `QUORUM_CONFIG` names, never one it finds, and resolves it. `define.ts` is `defineConfig` |
| `src/bench/` | The code of `quorum bench`, which reads a suite, runs its reviews and reports them. `suite.ts` reads and checks a suite with the config loader's own readers: the schema and its caps, the patches and the content hash. `score.ts` decides whether a review's findings catch a case's bug, and counts the kept findings that catch nothing. `stats.ts` holds the Wilson interval, the exact sign test and the nearest-rank percentile, written by hand and held to reference values. `fingerprint.ts` is the salted fingerprint of a resolved configuration. `records.ts` holds the formats of `run.json` and of a line of `results.jsonl`, as strict schemas. `run-dir.ts` is every read and write of a run directory, none of them through a symbolic link. `runner.ts` runs the planned reviews, each through a quorum of its own and at most `--jobs` at once, and hands each that resolved to a callback that records it. `report.ts` builds the report from the scores and renders it as Markdown and as JSON. [Benchmarks](../20-using/70-bench.md) says what each does for a user |
| `bench/` | The repository's own suites, `bench/bugs/` and the licenses of its cases in `bench/LICENSES/`: data for `quorum bench`, which no package, binary or image ships |
| `src/cli/` | The CLI: `bin.ts`, the process entry point, which holds exit code `3` until the run settles; `main.ts`, `runCli` and the usage; `io.ts`, the I/O a run gets, the exit codes of a review and the lines of a failure, which `main.ts` and `bench.ts` share; `bench.ts`, `runBench`, the subcommand's flags, plan, progress lines and exit codes, which `runCli` hands the arguments after `bench`; `render.ts`, the banner, the progress lines and the progress sink the CLI and `runQuorum` share; `print-config.ts`, the YAML of `--print-config` |
| `src/index.ts` | The public API, and the deprecated `runQuorum` |
| `schema/quorum.schema.json` | The JSON Schema of a YAML or JSON config, for editors: draft-07, generated from the file variant by `bun run schema`, which runs `scripts/schema.ts`, and committed |
| `scripts/` | The programs `bun run` starts, which no module of `src/` imports: `schema.ts` writes the JSON Schema (`bun run schema`), `build-binaries.ts` compiles the binaries of a release and their checksums (`bun run compile:release`), and `live-claude-code.ts` checks the `claude-code` adapter against the real `claude` (`bun run live:claude-code`). Specs beside them, `scripts/**/*.spec.ts`, run with the suite |
| `.github/workflows/` | `ci.yml`, which checks every pull request, and `cd.yml`, which builds and publishes the release: [The release](#the-release) |
| `src/testing/` | The test helpers, among them the `fetch` stub the adapter specs share, the provider contract suite every adapter's spec runs, each protocol's recorded replies, a fake `claude` (`fake-claude.mjs` and `claude.ts`) and the results of real Claude Code runs it replays, the bench's fixture suites and fake models (`bench.ts`) and the CLI's in-memory I/O (`cli.ts`). Spec files import them; `bun run lint` refuses an import from any other file |

## The dependency rule

The core knows no domain, no model vendor and no process. A profile is data, an adapter sees the core only through its port, and only the outer layers touch the process:

| Layer | May import | May not use |
| --- | --- | --- |
| `src/core/` | Other core modules, `zod`, `node:crypto` and the `package.json` version | The globals `process`, `fetch`, `WebSocket`, `EventSource`, `Worker`, `Bun`, `globalThis`, `global` and `self` |
| `src/profiles/` | Types from `src/core/`, and nothing else | The same globals |
| `src/providers/` | Its own modules, and `core/ports.ts`, `core/errors.ts` and `core/types.ts` | `process`, `Bun`, `globalThis`, `global` and `self`; it may use `fetch`, `WebSocket`, `EventSource` and `Worker` |
| `src/providers/claude-code.ts` | The same, and `node:child_process`, `node:fs`, `node:fs/promises`, `node:os` and `node:path` | `Bun`, `globalThis`, `global` and `self`; of the providers, it alone reads `process`, for its environment and its process group |
| `src/config/` | Its own modules, `src/core/`, `src/profiles/`, `src/providers/`, `zod`, `yaml`, `node:fs`, `node:fs/promises`, `node:path` and `node:url` | `fetch`, `WebSocket`, `EventSource`, `Worker`, `globalThis`, `global` and `self`; it may read `process` |
| `src/bench/` | Its own modules, `src/core/`, `src/config/`, `zod`, `yaml`, `node:fs`, `node:fs/promises`, `node:path` and `node:crypto` | The globals `process`, `fetch`, `WebSocket`, `EventSource`, `Worker`, `Bun`, `globalThis`, `global` and `self`; and never `src/cli/` or `src/testing/` |
| `src/cli/`, `src/index.ts` | Any layer but `src/testing/` | |

The core never imports a profile. No inner layer imports `src/bench/`: only `src/cli/bench.ts` does, which hands it the environment, the signal and the working directory it may not read for itself. `src/config/` reads the config file it is named, the prompt files that file names, and `process.env` when `loadConfig` or `fromConfig` is given no environment, `src/cli/` is the one module that reads the diff and stdin and writes stdout and stderr, and `runQuorum` in `src/index.ts` calls `loadConfig` with no options, so it reads `process.env` and the file `QUORUM_CONFIG` names, which must be an absolute path. The adapter in `src/providers/claude-code.ts` is the one module that starts a process, and `src/config/claude-code.ts` only looks its executable up, with `node:fs` and `node:path`. `bun run lint` enforces the table through the overrides at the end of [`eslint.config.js`](../../eslint.config.js), on every production file; a spec file may import across layers, and `src/testing/`. `src/lint.spec.ts` lints a probe file in each layer through ESLint's API, so a boundary that stops refusing an import or a global fails the suite.

## The stages of a review

`review` runs every profile of the quorum at once, on a diff split into one section per file once for all of them, under one concurrency limit. Before any stage, the harness reads the advisory flags from that split diff. Each profile goes through three stages on its own:

1. **Research.** One call to the profile's research provider, with its research instructions, the fenced diff and its guidelines. The reply is parsed strictly, only the first `maxFindings` findings it lists are read, and each is checked against the diff: a finding that cites code outside the diff is dropped, and one the harness cannot read is a gap. Each finding that passes the check is named by its id and tagged with its profile.
2. **Dedup.** Plain code drops a finding that repeats the file, line and category of an earlier one.
3. **Panel.** Every finding goes to every lens, each vote to the lens's own provider, each voter receiving the claim, the evidence, the diff section of the cited file, and the guidelines when the profile has them. The verdict is computed in code from the votes, by the profile's thresholds.

The result joins the profiles' verdicts and gaps in profile order, its `meta.usage` and `invalidFindings` are counted from the review's own events, its `meta.flags` holds the flags, and each event reaches the sink as a copy. Every stage and every call checks the review's signal: [Abort](./30-library-api.md#abort).

## The release

[`.github/workflows/cd.yml`](../../.github/workflows/cd.yml) cuts a release and publishes what it ships: the npm package, four binaries and a container image. It runs on every push to `main`, except one that only touches files under `.github/`, and by hand, and it calls the shared workflows of [`this-is-tobi/github-workflows`](https://github.com/this-is-tobi/github-workflows) at `@v0`. Every artifact is built in the run that creates the release, from the commit that release is tagged on: the jobs that check out the repository get the commit the push made, which for a release is the commit that merged the release pull request, the one release-please tags `v<version>`. `release-guard` fails a run that would release another commit's pull request, and `release-check` stops the package, the image and the attestations of a run whose release is tagged on another commit: the paragraphs on them below say what neither can do. No artifact is built anywhere else and attached afterwards.

| Job | Runs | Does |
| --- | --- | --- |
| `expose-vars` | On every push | Reads the Bun version pinned in `mise.toml` and hands it to the jobs that install Bun, so the binaries and the npm package are built with the Bun that the build stage of the `Dockerfile` pins too: [`src/dockerfile.spec.ts`](../../src/dockerfile.spec.ts) keeps the two equal |
| `build-binaries` | On every push | Installs the production dependencies from the frozen lockfile, running no lifecycle script, runs `bun run compile:release` and uploads `bin/release/` as the artifact `quorum-binaries`, which holds the four binaries and `SHA256SUMS` and nothing else, and expires after three days |
| `release-guard` | On every push, once `build-binaries` has passed | Fails the run when a merged release pull request is still labelled `autorelease: pending` and merged another commit than the run's: see below |
| `release` | On every push, once `build-binaries` and `release-guard` have passed | Calls `release-app` as the repository's GitHub App, so that the release pull request it opens runs CI. release-please opens or updates that pull request, and when it is merged `release-app` creates the tag `v<version>` and the GitHub release, moves the tags `v<major>` and `v<major>.<minor>` to that commit, and attaches every file of `quorum-binaries` to the release |
| `release-check` | Only when `release` created a release | Fails the run when release-please tagged the release on another commit than the run's, or reports none, so that the three jobs below do not run: see below |
| `attest-binaries` | Only when `release` created a release, once `release-check` has passed | Downloads `quorum-binaries` and attests the build provenance of the four binaries |
| `npm` | Only when `release` created a release, once `release-check` has passed | Calls `release-npm`, which installs from the frozen lockfile, runs `bun run build` and publishes the package with provenance |
| `docker` | Only when `release` created a release, once `release-check` has passed | Calls `build-docker`, which builds the `Dockerfile` for `linux/amd64` and `linux/arm64`, each on a runner of its own architecture, and pushes `ghcr.io/this-is-tobi/quorum` tagged with the version, its minor, its major and `latest`, and with the short commit SHA, which `build-docker` adds by default |
| `attest` | After `docker` | Calls `attest-docker` on the digest `docker` pushed |

`build-binaries` runs on every push because `release` attaches the binaries to the release it creates, and a push is not known to create one until `release` has run. So a push that creates no release uploads an artifact that expires unused, and a compile that fails stops `release` as well: no release pull request is opened or updated until it compiles again. Each job holds the permissions it uses and no others, none at the level of the workflow, and the checkouts of `cd.yml` itself keep no credential in `.git/config`.

`release-guard` keeps the tag and the artifacts on one commit. release-please releases every merged release pull request that is still labelled `autorelease: pending`, and tags that pull request's merge commit, whatever commit the run is on. If the run of a release commit fails before release-please, in `build-binaries` for instance, the next run on `main` would create that release from its own commit: the tag on the release commit, and the binaries, the package and the image built from the later one. `release-app` attaches the binaries itself, so the guard runs before it, right after `build-binaries`, to check when the release is about to run and not before minutes of compiling. It lists the merged release pull requests of the branch through the API, with `pull-requests: read` and no checkout, and fails the run, naming the pull request and its merge commit, when one is still pending and its merge commit is not the run's; a call that fails fails the guard too. The same check fails the run of a commit pushed to `main` while a release commit's run has not released yet.

`release-check` covers what the guard cannot see, a merge that lands after it. In the seconds between the guard and the moment release-please lists the pull requests, the release pull request can be merged, and the run that is already past its guard releases it: the tag is on the merge commit, but the binaries `release` attaches, and the commit the tags `v<major>` and `v<major>.<minor>` are moved to, are that run's. `release-check` runs after `release` when it created a release, with no permission and no checkout. It reads the commit release-please reports it tagged, and fails the run when that is empty or is not the run's commit, so `attest-binaries`, `npm` and `docker` do not run, nor `attest` after `docker`. It cannot take back what `release` did before it: the binaries and the moving tags may already be on the release, and the recovery below corrects them.

What recovers depends on whether the release exists. A run can be re-run up to 30 days after its first attempt, a re-run keeps the commit and the ref of the original run, and "Re-run failed jobs" also re-runs the jobs that depend on the failed ones and leaves the others their outputs, which the new jobs use: [Re-running workflows and jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).

- **The run of the release commit failed before the release existed**, in `build-binaries` for instance, or in `release` before release-please created the release: this is what the guard of a later run reports. Use "Re-run failed jobs" on that run. The failed job runs again with the jobs that depend on it, and `release` creates the release from the release commit.
- **A publish job failed after the release existed**: `attest-binaries`, `npm`, `docker` or `attest`. Use "Re-run failed jobs" on that run. `release` and `release-check` passed, so their outputs carry over, `release-created` and the version among them, and the failed job runs again from the release commit, with the jobs after it. `attest-binaries` also reads the artifact `quorum-binaries`, which expires three days after the run.
- **`release` failed after release-please created the release, or `release-check` failed.** "Re-run failed jobs" does not help. The release exists and its pull request is labelled `autorelease: tagged`, so a second `release` creates nothing and sets no `release-created`, and every job that waits for it is skipped for that version for good; `release-check` run again alone reads the same outputs and fails again. Delete the release and its tag (`gh release delete v<version> --cleanup-tag`), put the label `autorelease: pending` back on the release pull request in place of `autorelease: tagged`, then use "Re-run all jobs" on the run of the release commit, which is not the failed run when a run of another commit released it. It runs again from the release commit: the binaries are built again, release-please releases the pull request again, `release-app` moves the major and minor tags back to the release commit, and the jobs that publish follow.
- **A manual dispatch is none of these.** It builds the head of `main`, which is not the release commit once another commit follows it, so `release-guard` refuses it while a release is pending on another commit.

Where each artifact's attestation is:

- **The binaries.** One build provenance attestation per binary, none for `SHA256SUMS`: `attest-binaries` makes them with `actions/attest-build-provenance`, and GitHub stores them in the attestations of the repository. `gh attestation verify quorum-<target> --repo this-is-tobi/quorum` checks a downloaded binary against its attestation.
- **The image.** `attest-docker` signs the digest with cosign, keyless, and attaches an SPDX SBOM that Trivy generates with `cosign attest`, as an attestation of type `spdxjson`: both are stored in the registry beside the image. It also attests the build provenance, which goes to GitHub's attestations and to the registry. `gh attestation verify oci://ghcr.io/this-is-tobi/quorum:<version> --owner this-is-tobi` checks the provenance, and `cosign` checks the signature and the SBOM. The certificate of that provenance names two workflows. Its signer, which `gh` matches, is the `attest-docker` workflow of `this-is-tobi/github-workflows`, and it records this repository's `cd.yml` as the build configuration. Since `gh` matches the signer, the command names the owner and not the repository: `--repo this-is-tobi/quorum` alone refuses it.
- **The npm package.** `npm` publishes through npm's trusted publishing: the registry accepts the identity of the workflow run in place of a token, so the repository holds no npm token, and `--provenance` makes the publish fail rather than go out without its provenance. The registry holds the provenance statement of each version, which names the repository, the workflow file, the commit and the run that built it, and the package's page on npmjs.com links to the commit and the run. `npm audit signatures` checks it for a package a project installed.

Renovate decides whether a dependency bump cuts a release: release-please lists a `build` commit under Dependencies and cuts a patch release for it, and a `chore` commit does neither. [`renovate.json`](../../renovate.json) commits as `build` what the artifacts embed, the runtime dependencies, the Bun pin and the base images of the `Dockerfile`. The Bun pin of `mise.toml`, the `packageManager` field of `package.json` and the `oven/bun` tag of the `Dockerfile` move in one pull request, since the suite fails when the tag and the pin differ. The Node pin, the development tools and the CI actions stay `chore`. TypeScript stays below 7 until typescript-eslint, which the lint runs, supports it, since TypeScript 7.0 ships no JavaScript API.

## Testing

```bash
bun run test        # the whole suite, once
bun run test:cov    # the same, with coverage
bun run typecheck   # tsc --noEmit
bun run lint        # eslint, the Markdown pages and their code blocks included
bun run format      # eslint --fix
bun run schema      # write schema/quorum.schema.json from the zod schema
bun run build       # tsc: the npm package, into dist/
bun run compile:release   # the four binaries of a release and SHA256SUMS, into bin/release/
bun run live:claude-code   # four calls to the real claude CLI, by hand
```

- **`bun run test` runs Vitest under Node**, once, on every `src/**/*.spec.ts` and `scripts/**/*.spec.ts`. Never run bare `bun test`, which starts Bun's own test runner instead of the Vitest setup the specs are written for, and never run Vitest in watch mode.
- **At most two test workers**, set in [`vitest.config.ts`](../../vitest.config.ts), so the suite stays light on a laptop.
- **No network and no model call.** Every test uses fake providers, a stubbed `fetch` or a fake `claude`. The controls of the threat model are checked by structure in the default suite, such as no environment value in any request, and vote requests that are the same whatever the other voters answer.
- **`bun run test:cov`** measures coverage with Istanbul over `src/**/*.ts`, the specs and `src/cli/bin.ts` left out, and not over `scripts/`.
- **Files and processes.** `src/config/load.spec.ts` writes the files it reads to fresh temporary directories, removed afterwards, and runs one `node` process on the loader: vitest's own import transforms TypeScript that Node itself refuses, such as an `enum`, so only a real `node` shows what Node reports. `src/cli/main.spec.ts` writes its config files to a temporary directory too, and `src/cli/bin.spec.ts` runs `node` on `bin.ts`, for what only a process shows: the exit code it sets, a run that stops with nothing left to wait for, an error nothing caught, SIGTERM, and a second SIGINT. `src/lint.spec.ts` starts ESLint once, about a second, and lints a probe file in each layer through its API, in memory: it writes no file.
- **The bench.** The specs of `src/bench/` and `src/cli/bench.spec.ts` write their suites and their run directories to temporary directories, which each spec removes, and no spec calls a model: the runner and the command review with fake providers, and the command runs through `runCli` with fake I/O. `src/bench/suites.spec.ts` validates `bench/bugs/` in the default suite, as every run does, and holds its provenance, its licenses and its patch sizes.
- **The fake `claude`.** `src/testing/fake-claude.mjs` stands in for `claude`: it replays a captured result as its stdout and records its argv, environment, stdin, working directory and system file. Each spec reaches it through a `/bin/sh` wrapper in its temporary directory that runs this Node, so neither an execute bit in git nor `PATH` matters. Six requests spawn it: in `src/providers/claude-code.spec.ts` a round trip, an exit without JSON, a helper outside the group that holds the pipes while the stdout goes past 16 MiB, SIGTERM and SIGKILL, and in `src/cli/main.spec.ts` one review through the CLI. The first request on a command runs `claude --version` before its own run, which the fake answers with `2.1.311 (Claude Code)`, or `FAKE_CLAUDE_VERSION` after `FAKE_CLAUDE_VERSION_DELAY_MS`, and records on a line of its own, so it never overwrites the request's record. Three more tests run it for the version check alone, with a version that is too old, one that cannot be read and one that never answers (a delay far past the deadline, which the spec shortens by holding that one timer to 0.4 s). One more call in the adapter's spec fails to spawn at once, with a command that does not exist. The adapter's spec points `TMPDIR` at its own directory, to see every run directory go.
- **`bun run live:claude-code`** is not part of the suite: no test and no CI job runs it. You run it by hand, with Claude Code installed and logged in, and it makes four real calls on `haiku`, each capped at $0.05, from a directory that holds a planted `CLAUDE.md` and a canary file: structured output, the `prompt` mode, a message that names the canary file as `@<its path>`, and the error of an unknown model. It passed against Claude Code 2.1.311 at under a tenth of a cent: [Stopping, nesting and the version](../20-using/30-providers.md#stopping-nesting-and-the-version).
- **`src/config/schema.spec.ts`** fails when `schema/quorum.schema.json` differs from the JSON Schema of the zod schema, byte for byte: run `bun run schema` after changing the schema, and commit the file.
- **`bun run build`** writes the npm package into `dist/`, which is not committed: the JavaScript of `src/`, its relative imports rewritten to `.js`, and the declarations, with no spec and nothing of `src/testing/`, as [`tsconfig.build.json`](../../tsconfig.build.json) says. No test builds it: [`src/package.spec.ts`](../../src/package.spec.ts) reads `package.json`, that file, `release-please-config.json` and the first line of `src/cli/bin.ts`, for what the package names, ships and runs on, and for the `.env` and `bunfig.toml` flags of `bun run compile`. The `typecheck` job of `ci.yml` runs the build after the typecheck, on every pull request: the build sets a `rootDir`, emits declarations and rewrites the import extensions, which `tsc --noEmit` does not, so a change can pass the typecheck and fail the build, and the release's own run is not the first to build the package.
- **`bun run compile:release`** compiles the binaries of a release, `quorum-linux-x64`, `quorum-linux-arm64`, `quorum-darwin-x64` and `quorum-darwin-arm64`, and writes them with a `SHA256SUMS` file to `bin/release/`, which is not committed. [`scripts/build-binaries.ts`](../../scripts/build-binaries.ts) empties `bin/release/` first, runs `bun build --compile` once per target with the flags of `bun run compile`, so no binary reads a `.env` or a `bunfig.toml` from the directory it runs in, and writes the checksums only when all four builds succeeded. It builds only when it is run directly, and no test compiles a binary: [`scripts/build-binaries.spec.ts`](../../scripts/build-binaries.spec.ts) checks the arguments of the four builds, the checksum line against a known digest and that importing the script starts no build, with `node:child_process` mocked.
- **`src/cd.spec.ts`** reads `.github/workflows/cd.yml` as data, with no network: that the workflow grants nothing at its top level and each job exactly the permissions it uses, that `release-guard` holds `pull-requests: read` alone, waits for `build-binaries` and compares merge commits with the run's, that `release` waits for it and attaches the artifact `build-binaries` uploads, that `release-check` holds no permission and compares the commit release-please tagged with the run's, failing on an empty one, that `attest-binaries` attests the four binaries and not `SHA256SUMS`, that the attestations, the package and the image are made only when a release is created and wait for `release-check`, that `npm` passes no token, and that every `uses:` is a catalog workflow at `@v0` or an action pinned by a commit SHA. Nothing in the suite runs the workflow, publishes or reaches a registry.
- **`docker build -t quorum:local .`** builds the image from the [`Dockerfile`](../../Dockerfile): a build stage on Bun's image installs the production dependencies from the frozen lockfile with no lifecycle script and runs `bun run compile`, and a final stage on a distroless `cc` base holds that one binary, run as `nonroot`. Both base images are `ARG` defaults pinned by tag and digest, which Renovate updates. No test builds an image: [`src/dockerfile.spec.ts`](../../src/dockerfile.spec.ts) reads the `Dockerfile` and the [`.dockerignore`](../../.dockerignore) for the pins, the Bun version of `mise.toml`, the install and compile steps, the user, the entrypoint and what stays out of the build context.
- **`bun run lint`** applies `@antfu/eslint-config` and the dependency rule. From an editor's terminal, run it as `CI=1 bun run lint`: the config turns some rules off when it detects an editor.
- **`src/docs.spec.ts`** holds these pages to their links: every relative link resolves to a file and every anchor to a heading of it, every page outside the start page and the reference section ends with a `## Next` that names one page, the table of contents in the README's `## Documentation` section lists every page, and neither the README nor any page holds a hidden character.

When you commit, the Git hooks that `bun install` sets up run lint-staged, which runs eslint on the staged files, and commitlint on the message, which must follow Conventional Commits.
